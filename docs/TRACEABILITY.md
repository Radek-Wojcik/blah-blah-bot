# Requirements traceability

This document maps each of the 52 product requirements to the tests, measurements or demo steps that show it is met, and states plainly where it is not. It describes `main` after Stages 5 and 6 (`v0.7.0`) merged into the Stage 8 prep branch. Rows for Stage 7 stay "Pending merge" until Stage 7 is merged.

## How to read this document

**Status**

| Status | Meaning |
|---|---|
| Covered | Implemented in `main`, with automated tests or a recorded measurement that is referenced |
| Covered (manual) | Shown by a document or a demo step rather than by an automated test |
| Covered, gap noted | Implemented and tested, but a quality or coverage gap exists; the gap is listed in [Gaps](#gaps) |
| Pending merge | Belongs to a feature of Stage 5, 6 or 7 that is not in `main` yet; whatever already exists is listed |
| Reduced for 1.0 (pending merge) | As above, with the narrower scope agreed for version 1.0 (see [Agreed scope for 1.0](#agreed-scope-for-10)) |
| Gap | Not met as stated; see [Gaps](#gaps) |

**Evidence.** A reference in backticks has the form `path::test name`. For Rust and Python it is the test function; for TypeScript it is the title of the test (or part of it). A reference with the prefix `stage5:` names a test or file that exists on the Stage 5 branch only. A bare path is a document, a schema or a result file. `Demo M1` to `Demo M5` are the manual steps at the end of this document.

**Stage** is the stage of the [roadmap](ROADMAP.md) that delivers the requirement.

**Check.** `python scripts/check_traceability.py` verifies that every referenced file, test and title exists, that all 52 numbers are present, and that the summary below matches the table. It needs only Python and git, and runs in about a second.

## Agreed scope for 1.0

- **Export (requirement 44):** tasks are exported to Notion only. Todoist and Trello are not part of 1.0.
- **Discord bot (requirement 40):** a text bot (member lookup, a thread per meeting, editing a published message). It does not join voice channels and does not record.
- **Tab groups (requirement 18):** Chrome lets an extension capture only the tab on which the user invoked it, so a tab group is captured with one action per tab, guided by the extension. Tabs added later need one more action. Capturing the whole browser is the fallback.

## Gaps

These are the places where a requirement is not met as stated, or where "covered" does not mean "measured on real use".

| ID | Gap | Rows |
|---|---|---|
| G1 | **Quality on real speech is not measured.** Word error rate, speaker error rate, term recall and extraction quality come from synthetic recordings. Three Stage 0 targets are missed on synthetic data and kept unchanged: term recall (best 51%, target 85%), translation rate (best 1.3%, target 1%) and speaker error rate for 2 to 4 speakers (20.5% to 23.3%, target 15%). Per-meeting task recall of the default model is 43.5% to 100% on Polish and mixed meetings. See ADR 0003, 0004 and the README measurements. | 2, 25, 26, 35 |
| G2 | **Windows 11 is not tested,** neither recording nor installation. Windows 10 was verified on build 19045 only. | 1 |
| G3 | **Real Teams and Discord calls are not captured by hand.** Per-application capture was measured with test processes. Behavior of the new Teams client (which process plays the sound) is unknown. | 17 |
| G4 | **15 to 30 participants.** Measured up to 16 speakers (error rates of 21.3% and 27.4%, reported without a target). Separating more than about 8 voices from one mixed track is not promised; separate source tracks, the participant list and voice profiles are the mitigations. | 23 |
| G5 | **Microphone discontinuity flags.** In the 10 hour run the audio engine flagged 194 discontinuities on the microphone track (about one every 3 minutes) although the audio was continuous and its length exact; the zero-loss target is not met for the microphone and the cause is unexplained. Application tracks had none. | 16, 20 |
| G6 | **Real-application end-to-end tests are unreliable.** `npm run test:real` has not passed since Stage 3 in sessions where the user is away or remote (the web view of the application is closed by the system). Real-application behavior is covered by the mock suites plus manual runs. | 10, 17, 19, 20 |
| G7 | **Multiple monitors with mixed scaling** are tested only with synthetic frames, not on real hardware. | 12 |
| G8 | **No image inside the report text.** Screenshots are described and placed in the transcript by time. The report renderer does not embed images; Stage 5 publishes screenshots as files next to the report and attaches them to Discord messages. Whether the report should also reference them at their time position is to be decided when Stage 5 is merged. | 21 |
| G9 | **The cycle's transcription settings are not applied.** `languages.asr` and the glossary are stored in the cycle, and the glossary reaches extraction, but transcription always runs with automatic language detection and without a glossary prompt, which is also the configuration that was measured. The speaker bound from the participant list is not applied either. | 2, 24 |
| G10 | **Echo is not removed.** Sound from the speakers that the microphone picks up appears in both tracks. | 16 |
| G11 | **The 10 hour end to end run is not done.** The 10 hour estimate (about 86 minutes) is the sum of separately measured stages: transcription and speaker separation from Stage 0, extraction and reduce from Stage 4. Vision, publishing and model loading are not included. | 23 |
| G12 | **Other backends are not tested live.** Language model servers other than `llama-server` (Ollama, LM Studio) and the cloud path are tested against mock servers only. | 29, 30 |
| G13 | **No automated scan for hard-coded paths.** CI scans files and history for secrets and checks the size and type of files; absolute paths in the source are checked by review before a release. | 51 |

## Manual demo steps

- **M1. Recorder.** Start the application, open the widget from the tray icon, press Record, pick the microphone and one application, add a second application while recording, press Stop. The meeting list shows a meeting with three tracks.
- **M2. Screenshot.** While recording, press the screenshot hotkey (Ctrl+Alt+S by default), drag a rectangle, release. The meeting shows a screenshot with its offset; the cropped image matches the selection.
- **M3. Recovery.** Start a recording, end the application process from the task manager, start the application again. The meeting is listed as recovered; recovering it keeps all complete segments.
- **M4. Processing.** With the models set up, process a recorded meeting. The queue shows each stage, waits while another program uses the GPU, and finishes with a transcript with speakers and described screenshots.
- **M5. Draft.** Process a meeting of a cycle with a language model configured. Open the draft, open the source of an item (quote, time, jump to the transcript), change the report mode and move an item to another section.
