# Testing strategy

## 1. Principles

- Fast tests run on every push. Tests that need a GPU or real models run locally before each release and their results are published with the release.
- Model quality is measured, not assumed. Every model-dependent feature has a labeled data set, a metric and a threshold.
- Test data never contains real meetings or real people. Audio is scripted or synthetic.
- Schemas are the contract between components and are tested from both sides.

## 2. Test levels

| Level | Scope | Tools | Runs |
|---|---|---|---|
| Unit (Rust) | Journal, queue state machine, GPU guard decisions, template rendering, message splitting, cycle file validation | `cargo test` | CI |
| Unit (Python) | Windowing, quote matching, deduplication, metric code, merge of tracks | `pytest` (CPU only, no models) | CI |
| Unit (TypeScript) | UI state, formatting, bridge protocol in the extension | `vitest` | CI |
| Contract | JSON Schemas validated against fixtures produced by Python and consumed by Rust and the UI | Schema validators in each language | CI |
| Integration | Recorder with a virtual audio device; pipeline with real models; publishers against mock servers | Dedicated harness | Recorder and publishers in CI where possible; models locally |
| End-to-end | User flows through the UI | Playwright on the UI with a mock backend; smoke test of the packaged application | UI flows in CI; packaged smoke test locally |
| Measurement | Quality and performance on the reference machine | `benchmarks/` | Locally, before each release |
| Resilience | Faults injected during recording, processing and publishing | Scripts in `benchmarks/resilience/` | Locally, before each release |

## 3. Test data

| Set | Content | Ground truth | Location |
|---|---|---|---|
| `tones` | Generated sine sweeps and clicks per track | Exact sample positions | Generated in the test |
| `mini` | Three clips of 30–60 s: Polish, English, mixed | Transcript, speakers | Repository (small files) |
| `scripted` | Scripted meetings of 10–30 min, 2–10 voices, with planted tasks, owners, dates, decisions and budget figures; Polish, English and mixed | Script and annotation file | Outside the repository, regenerated from scripts |
| `long` | Concatenation and variation of `scripted` up to 10 h | Derived | Generated |
| `extraction` | 10 scripted transcripts (4 Polish, 3 English, 3 mixed) with planted tasks, assignees, due dates, decisions and budget figures | Annotation file written together with the script | Generated by `benchmarks/src/bbb_bench/datasets/make_sets.py`; text only, regenerated rather than committed |
| `slides` | Demo slides, charts and diagrams as images | Key facts per image | Repository |
| `demo` | Fictional cycle with fictional participants for screenshots and demos | Not applicable | Repository |

- Scripts and annotations are versioned. Audio for the larger sets is produced from the scripts with a text-to-speech tool or recorded by volunteers reading them, and is not committed.
- The mixed-language scripts use Polish sentences with English technical terms from a glossary, so term recall can be scored.

## 4. Metrics

| Metric | Definition |
|---|---|
| WER | Word error rate after normalization (case, punctuation, numerals) |
| Term recall | Share of glossary terms transcribed correctly |
| Translation rate | Share of segments output in a language other than the spoken one |
| DER | Diarization error rate, no collar, overlap included |
| Speaker accuracy | Share of speech time attributed to the correct named participant |
| False accept rate | Share of unknown voices assigned to a known profile |
| Task recall and precision | Against labeled tasks; a match requires the same action and object |
| Assignee and due-date accuracy | Among correctly found tasks |
| Quote validity | Share of items whose quote is found in the transcript near the stated time |
| Schema validity | Share of model responses valid after the allowed retries |
| RTFx | Audio duration divided by processing time |

## 5. Thresholds

Targets for the reference machine (RTX 3080 12 GB, 32 GB RAM). Stage 0 measures the baselines; a missed target triggers the decision gate.

**Recorder**

| Measure | Target |
|---|---|
| CPU while recording three tracks | 3% of total CPU on average or less |
| Memory | 200 MB or less |
| Dropped buffers in a 10-hour run | 0 |
| Audio lost when the process is killed | 60 s or less per track |
| Track alignment error | 50 ms or less |

**Transcription and speakers**

| Measure | Target |
|---|---|
| WER, Polish scripted set | 15% or less |
| WER, mixed set | 20% or less |
| Term recall, mixed set | 85% or more |
| Translation rate | 1% or less |
| DER, 2–4 speakers | 15% or less |
| DER, 6–10 speakers | 30% or less |
| DER, 15+ speakers | Measured and reported; no target |
| Speaker accuracy for enrolled voices (turns of 5 s or longer) | 90% or more |
| False accept rate | 2% or less |

**Extraction**

| Measure | Target |
|---|---|
| Schema validity (up to two retries) | 100% |
| Task recall | 80% or more |
| Task precision | 80% or more |
| Assignee accuracy | 85% or more |
| Due-date accuracy | 85% or more |
| Quote validity | 95% or more |

**Processing time**

| Measure | Target |
|---|---|
| 2-hour meeting, full pipeline | 45 min or less |
| 10-hour meeting, full pipeline | 4 h or less |
| Peak VRAM in any stage | 11.5 GB or less |

Regression tolerance after Stage 0: quality metrics may not drop by more than two percentage points against the recorded baseline without an explicit decision.

## 6. Resilience tests

| Fault | Expected result |
|---|---|
| Recorder process killed during recording | Meeting recovered, loss within the threshold |
| Captured application closed during recording | Its track ends, others continue |
| Audio device unplugged | Track ends cleanly, notification shown |
| Disk nearly full | Recording stops with a clear message, existing segments intact |
| Worker killed in each stage | Retry resumes from that stage |
| GPU occupied by another process | Job waits; starts when the GPU is free |
| Model server returns invalid JSON | Retries, then a flagged window |
| No network at briefing | Cached state with its date |
| No network at publishing | Outbox, automatic retry |
| Concurrent push to the cycle repository | Rebase and retry succeeds |
| Extension service worker restarted | Stream reconnects; gap recorded in the journal |

## 7. Model comparison set

The `extraction` set is used to compare language models and prompts under identical conditions: same transcripts, same schema, same scoring script. A run records model name, quantization, context size, backend, speed and all extraction metrics. Results are stored as JSON under `benchmarks/results/` and summarized in the README. A model becomes a default only with a recorded run.

## 8. UI tests and reproducible screenshots

- The UI runs against a mock IPC layer that serves the `demo` data set, so tests need no audio devices, models or network.
- Playwright drives the flows listed in the roadmap for each stage.
- A screenshot script opens fixed routes at a fixed window size, theme and scale, and writes PNG files to `docs/img/`. Running it twice on the same commit produces identical images.
- Demo GIFs are captured from the packaged application in demo mode with a fixed script of actions.

## 9. Publishing tests

- Mock HTTP servers emulate the GitHub and Discord endpoints used by the publishers, including error and rate-limit responses (Notion arrives with its publisher in Stage 7); the Git side runs against local bare remotes. Details are in section 14.
- Before each release the publishers run against a dedicated test repository and a test Discord webhook (and, from Stage 7, a test Notion database). Credentials for these exist only on the release machine, in the Windows Credential Manager.
- Limits are tested at the boundary: message length, number of embeds, number and size of attachments.

## 10. Continuous integration

Workflows on Windows runners:

| Job | Content |
|---|---|
| `lint` | `cargo fmt --check`, `cargo clippy`, ESLint, Prettier, Ruff |
| `test` | Rust, Python and TypeScript unit tests; contract tests |
| `ui` | Playwright flows on the mock backend |
| `build` | Debug build of the application and the extension |
| `checks` | Secret scanning over files and history; commit message convention; no large or binary files outside allowed folders |
| `release` (on tag) | Installer build, checksums, draft GitHub release |

A pull request or push is mergeable only when all jobs pass.

## 11. Stage 2 test commands

| What | Command | Runs |
|---|---|---|
| Queue, GPU guard on recorded NVML traces, retention rules, transcript edits, runner | `cargo test -p queue` | CI |
| Worker: merge of tracks, schemas, manifest, vision prompt | `cd worker && uv sync --frozen --only-group dev && uv run --no-sync pytest` | CI |
| Contract: the same transcript fixture (`worker/tests/fixtures/transcript.json`) is validated against `schemas/transcript.schema.json` by Python and by Rust, and loaded into the Rust types without loss | `cargo test -p queue transcript`, `pytest tests/test_contracts.py` | CI |
| Pipeline on the short reference recordings with real models (valid transcript, speakers, WER against the Stage 0 baseline, no network, killed step leaves no partial file, slide facts) | `cd worker && BBB_MINI_DIR=... BBB_SLIDES_DIR=... BBB_VISION_DIR=... BBB_LLAMA_SERVER=... uv run pytest -m models` | Locally before a release |
| Whole job through the supervisor with the real worker: end to end, audio kept when the setting says keep, audio removed only after the audio stages, worker killed in each stage and resumed, GPU occupied by another process | `cargo test -p queue --test pipeline_models -- --ignored --test-threads=1` | Locally before a release |
| Time and peak VRAM for a 2 hour recording, per stage | `cd benchmarks && uv run python -m bbb_bench.proto.stage2_pipeline --audio ... --hours 2 --slides ... --worker-python ../worker/.venv/Scripts/python.exe` | Locally before a release |

The GPU guard is tested on recorded traces: a real trace of the idle reference machine (`crates/queue/tests/traces/idle-recorded.json`, recorded with the `record_gpu_trace` example, process ids replaced by their order) and traces derived from it for a busy GPU, a load that ends, a short spike and memory held by another process.

|---|---|---|

## 13. Stage 4 test commands

| What | Command | Runs |
|---|---|---|
| Cycle files, templates, git handling, issue cache, context builder and report rendering (`cycle-store`); schema v4 migration from v3 data, report settings, backend choice and cloud confirmation, cycle participants (`store`); extract and reduce stages with the GPU gate per backend, cloud refusal, key redaction, context and named transcript, draft editing operations and rendering, contract tests on the shared fixtures, and a job through the supervisor with a fake worker script (`queue`) | `cargo test -p cycle-store -p store -p queue` | CI |
| Worker: windows, quotes, deduplication, language, extract and reduce steps against a mock server, contracts on the shared fixtures | `cd worker && uv sync --frozen --only-group dev && uv run --no-sync pytest` | CI |
| Draft editor, report mode choice, backend dialog and cycle screens on the mock backend | `cd ui && npm test && npm run test:e2e` | CI |
| Extraction quality on the reference meetings (precision and recall of items, wrong assignee rate, quote verification, time per hour of audio, per model and backend). Runs the production `extract` and `reduce` steps as the queue does and writes `benchmarks/results/stage4-extraction-<name>.json`. `--hours N` runs a timing check on N hours of repeated transcript (`stage4-long-<name>.json`); `--modes` runs `reduce` in all four report modes on the first meeting (`stage4-modes-<name>.json`); other options: `--mode`, `--ctx` (default 16384), `--output-language`, `--worker-python`, `--work` | `cd benchmarks && uv run python -m bbb_bench.proto.stage4_extraction --model <GGUF> --name <run name> --meetings data/extraction/* --llama-server <llama-server.exe>` | Locally, when the model or the prompts change |
| Whole pipeline of the synthetic meetings `pl-03` and `en-03` as meetings of a cycle, with the real worker, the real GPU guard and a managed `llama-server` (context 16384): all nine stages done, `work/draft.json` valid against the schema, items with a verified quote, language resolved, source times inside the meeting, report rendering, and draft editing in report modes `fixed`, `auto` (Polish meeting) and `template`. Prints stage timings and item counts | `BBB_AUDIO_DIR=... BBB_LLM_MODEL=<GGUF> BBB_LLAMA_SERVER=... cargo test -p queue --test stage4_models -- --ignored --test-threads=1 --nocapture` | Locally before a release; GPU needed |

Extract and reduce with the real model through `llama-server` are covered by the whole-pipeline test above; the Python worker tests marked `models` cover the Stage 2 steps only.

The fake worker in `crates/queue/tests/stage4_fake_worker.rs` is a small Python script started in place of `python -m bbb_worker`; it needs only a Python 3 interpreter on `PATH`, no models and no GPU. Cloud is tested against a mock server only; no test sends text to a hosted service.

## 14. Stage 5 test commands

| What | Command | Runs |
|---|---|---|
| Unit tests for the Git side against local bare remotes in temporary folders: new files only, folder suffixes `-2` and `-3`, a push refused by a concurrent commit and built again on the new tip, three tries then left for later, `topics.yaml` merged per topic with a recorded conflict, an unrelated uncommitted file left alone and the branch fast-forwarded, a repository without a remote, an answer lost after the push (idempotent), a remote that is not there and then is, the token only in the environment of Git and never in its arguments, Git output scrubbed; issue markers, the issue cache and closed or linked issues in the context; the published transcript with its anchors (`cycle-store`, `queue`) | `cargo test -p cycle-store -p queue` | CI |
| Status proposals: `status_changes` in the extraction answer (verified and unverified quotes, unknown targets dropped, one proposal per target, an older `windows.json` without the field), the schemas and the shared fixtures from both sides | `cd worker && uv sync --frozen --only-group dev && uv run --no-sync pytest` | CI |
| Rules of the targets (`auto`, `on-approval`, `off` and their defaults), the publish plan, the public-repository check, the frozen snapshot and the draft lock, the outbox dispatcher (claim, execute, backoff and `Retry-After`, offline pause, crash recovery, progress of a Discord post), against a local bare Git remote, a fake GitHub and a fake Discord webhook (`publishers`); the outbox state machine, a Discord post held for the issues of its meeting, operations enqueued again after a cancel (`store`); status decisions in the draft (`queue`); planning, publishing, the lock, the `auto` rule, the tasks of a cycle and the check for a public repository through the command layer (`app`) | `cargo test -p publishers -p store -p queue -p app` | CI |
| The whole loop on a demo-like cycle (approved status changes, report, transcript, screenshots and `topics.yaml` in the remote, issues with assignee, due date and report link, an issue closed on the fake GitHub that is done in the next context, a Discord message with mentions and issue links) | `cargo test -p publishers --test full_loop` | CI |
| Faults: no network at publishing and recovery through the outbox, a push rejected by a concurrent commit and built again on the new tip, a remote that keeps changing, an answer lost after an issue or a comment was created (no duplicate), a rate limit, a crash while an operation runs, and a scan of the database file, the snapshots, the working tree, the history of both repositories, the log of the dispatcher and the outbox rows for the mock token and webhook | `cargo test -p publishers --test resilience` | CI |
| Status changes, the publishing panel, the outbox, the public-repository dialog, the report and Discord previews and the token setup (components and the mock backend, with the fake publishing lab of the mock) | `cd ui && npm test && npm run test:e2e` | CI |
| The images and the GIF of publishing in the README (`status-approval.png`, `publishing-panel.png`, `report-rendered.png`, `discord-message.png`, `token-setup.png`, `approve-and-publish.gif`), regenerated on the mock backend | `cd ui && npx playwright test --project=screenshots -g "status approval|publishing panel|rendered report|Discord message|token setup|approve statuses"` | Locally, when the screens change |
| Release check against the real services: a test GitHub repository (token and push rights, an issue created once, closed with a comment and read back, a commit pushed to a new branch that is removed again) and a test Discord webhook (the webhook exists, one message is posted) | `BBB_RELEASE_CHECK=yes BBB_RC_REPO=<owner/name> BBB_RC_DISCORD_REF=<cred:...> cargo test -p app release_check -- --ignored --test-threads=1 --nocapture` | Locally before a release |

Every test is written against fakes: the "network" is loopback ports that the tests start, the "remote" is a bare repository in a temporary folder, and "offline" is a closed port or a renamed folder. No normal test talks to a real host.

**The fakes.** `crates/publishers/src/testing/` (feature `test-support`, used by this crate's tests and by `app`) holds hand-written servers on `TcpListener` and a lab that wires them together:

| Fake | What it models |
|---|---|
| Fake GitHub | Repositories with visibility, push permission and owner type; issues with labels, assignees, comments, state, paging and `Link` headers; the organization issue-field endpoints; primary and secondary rate limits |
| Fake Discord webhook | The 2000 character, 10 file and size limits, `allowed_mentions` checks, `?wait=true`, multipart bodies, 429 with `retry_after` |
| Fault injection (both) | A given status for the next N requests, a dropped connection, a delay, "offline" as a closed port |
| Lab | A bare remote, a clone, a file database and a manual clock, so backoff and `Retry-After` are tested without waiting |

No HTTP mocking crate is used (it would pull `tokio` and `hyper` into the build). The fake GitHub implements the organization issue field as the documentation describes it, which is not proof that a real organization behaves the same way: the real check is in the release check below.

**The unit level.** Besides the rows above, `cargo test -p publishers` covers: error classification (408, 5xx, 429, a 403 that is a rate limit, other 4xx), `Retry-After` and rate-limit reset parsing, redaction of tokens, authorization values and webhook URLs, webhook address validation, message splitting at exactly 2000 and 2001 characters, in multibyte text and in one long line, 10 and 11 files, the size boundary and a skipped oversized file, mention rendering for users, roles and unknown ids, `@everyone` neutralized, `allowed_mentions` per message, the multipart body, resuming after the messages already sent, the issue body and marker, and the plan for each rule.

**Resilience.** `crates/publishers/tests/resilience.rs` covers: no network for every target and recovery; a dead Discord that does not hold back the report or the issues; a push rejected by a concurrent commit; a remote that keeps changing; an answer lost after an issue was created (no duplicate), after a crash too; a status change written once when answers are lost; Discord's 429 waiting for the time named; a GitHub rate limit pausing only that operation and a permanent error stopping at once; a crash while an operation runs; and the scan for secrets. `crates/publishers/tests/full_loop.rs` runs a demo-like meeting through all targets, an issue closed on the fake GitHub that is done in the next context, and a second meeting on the same day.

**The release check.** The tests of `crates/app/src/release_check.rs` are `#[ignore]`d and refuse to run unless `BBB_RELEASE_CHECK=yes` is set. They use a throwaway repository and webhook that exist only for this purpose:

| Variable | Meaning |
|---|---|
| `BBB_RELEASE_CHECK` | Must be `yes`; without it every check stops at once. |
| `BBB_RC_REPO` | The GitHub test repository, `owner/name`. It needs Issues and a token with write access. A public repository is refused unless `BBB_RC_ALLOW_PUBLIC=yes`. |
| `BBB_RC_GITHUB_API` | Optional API address (GitHub Enterprise Server); the public GitHub when absent. |
| `BBB_RC_DISCORD_REF` | The `cred:` reference of the test webhook, for example `cred:discord/release-check`. |

The secrets are not variables: the GitHub token (`github-token@<host>`) and the webhook (`target:<reference>`) are the entries that the application stores in the Windows Credential Manager from its publishing settings. Enter them there, on the release machine, never in a chat or a file. The checks leave a closed issue labelled `cycle:RC<time>` in the test repository, because an issue cannot be deleted through the API.
